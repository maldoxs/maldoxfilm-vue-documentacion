# ADR-004 — Resolución RD server-side (addMagnet→transcode) en vez del proxy de Torrentio

- **Estado:** Aceptada — implementación en curso (2026-06-10)
- **Decisores:** usuario (Angelo) + análisis técnico

## Contexto

El flujo de `rdGetStream` tenía dos caminos:
- **Cacheado** (`rdId` encontrado en `/downloads`): `GET /streaming/transcode/{rdId}` →
  DASH/HLS desde el CDN de RD. ✅ Correcto (Range OK vía Shaka, sin Torrentio).
- **No cacheado** (sin `rdId`): `resolveProxyUrl` seguía el redirect de Torrentio; si no
  lograba adoptar la URL CDN, **reproducía la URL `torrentio.../resolve/{TOKEN}/...`**.

Problemas del segundo camino (confirmados en logs):
1. **Torrentio actúa como puente de streaming** → se satura y **rompe los HTTP Range
   Requests** (sin seeking fiable).
2. **El RD_TOKEN viaja en la URL pública** (`/resolve/{TOKEN}/`) → visible en consola/Network.
3. **No dispara cacheo**: si el torrent no está cacheado, no hay forma de reproducirlo
   (caso "Weapons"). El workaround previo (buscar otra versión ya cacheada en el pool)
   es un parche, no la solución.

## Decisión

Reemplazar el camino **no-cacheado** por el flujo oficial de la API de Real-Debrid v1.0,
ejecutado **server-side** (Netlify Function), eliminando el proxy de Torrentio de la
reproducción. Enfoque **HÍBRIDO**:

- **Mantener intacto** el camino cacheado actual (downloads → transcode DASH). No se toca.
- **Agregar** el flujo nuevo SOLO cuando no hay match cacheado:
  1. `POST /torrents/addMagnet` (`magnet:?xt=urn:btih:{infoHash}`) → `torrent_id`
     (maneja error 33 "ya activo" reusando el torrent existente).
  2. `GET /torrents/info/{id}` → elegir el archivo de video más grande.
  3. `POST /torrents/selectFiles/{id}` → dispara cache/descarga.
  4. `GET /torrents/info/{id}` → si `status === 'downloaded'` y hay `links`, continuar;
     si no (RD descargando), devolver `ready:false` → respaldo iframe.
  5. `POST /unrestrict/link` → URL CDN directa (Range OK) + `download_id`.
  6. `GET /streaming/transcode/{download_id}` → **DASH como vía principal** (multi-audio
     + Range vía Shaka); **`liveMP4` solo como fallback**; HLS como segundo fallback.

- **Torrentio queda SOLO como índice**: se usa para obtener `infoHash` + filename del
  stream elegido; su URL `/resolve/` NO se usa para reproducir.

### Seguridad (clave)
Todas las llamadas a `api.real-debrid.com` van en la **Netlify Function `rd-stream`**
(server-side) → el **RD_TOKEN nunca llega al navegador** (header `Authorization` solo en
el servidor) y se elimina el CORS. Esto materializa la "Fase 2" descrita en `security.md`
para este camino.

### Manejo de errores RD
Reintento con backoff ante **429 / error 34** (too many requests) y **error 5** (slow
down). Manejo de **33** (torrent ya activo), **21** (demasiados torrents activos) y
estados `downloading`/`magnet_error`/`dead`.

## Consecuencias

- (+) Sin puente de Torrentio: **Range Requests/seeking correctos** y **token fuera del cliente**.
- (+) **Dispara cacheo** → reproduce contenido no cacheado (resuelve "Weapons" de raíz).
- (+) Mantiene multi-audio (DASH/Shaka) y el camino cacheado que ya funciona.
- (−) **Desviación del original** (`index.html` no usa `addMagnet`) — mejora deliberada.
- (−) `addMagnet` **escribe** en la cuenta RD → considerar limpieza de torrents y límites
  (error 21). Posible acumulación en la lista de torrents del usuario.
- (−) Latencia extra (~5-6 llamadas RD) en el camino no-cacheado; el cacheado sigue igual.
- (−) Si el torrent no está cacheado en RD, sigue sin reproducirse al instante (RD lo
  descarga) → respaldo iframe mientras tanto.

## Plan de implementación (paso a paso, tests verdes entre pasos)

6. Actualizar `integrations.md` / `player.md` / `security.md`.
