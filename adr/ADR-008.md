# ADR-008 — RD-mediaInfos como pipeline canónico de reproducción (+ atajo directo-Range)

- **Estado:** 🟡 PROPUESTA (a implementar 2026-06-14, por fases)
- **Decisores:** usuario (Angelo) + diseño técnico
- **Basado en:** investigación de la API de Real-Debrid (sesión 2026-06-13, §6) — usuario + ChatGPT.
- **Relacionada/absorbe:** el cambio de scoring "MP4+H264 primero" pendiente; ADR-004 (rd-stream),
  ADR-005 (subtítulos), ADR-007 (TV).

## Contexto
RD expone `/streaming/mediaInfos/{id}` → `details` (pistas del origen), `availableFormats`
(m3u8/mpd/liveMP4/webm), `availableQualities` (full/720p/480p) y el **`modelUrl`**:
`/t/{id}/{audio}/{subtitles}/{audioCodec}/{quality}.{format}`. Es la API real de transcode+
packaging que usa el player oficial de RD. MaldoxFilm ya la usa parcialmente (`fetchTranscode` +
`dashBaseUrl`), pero solo para x265/dual-lat. Hoy reproducir el .mkv crudo de Torrentio causa:
HEVC audio-sin-imagen en TV, MKV no-seekable, audio AC3/DTS no reproducible, incompatibilidad iOS.

## Problema
Unificar la reproducción para lograr compatibilidad universal (desktop/Android/iOS/TV) + cambio de
audio/subs + seek lo más rápido posible, con cero infraestructura propia (sin encode/CDN).

## Decisión (propuesta)
**Jerarquía por SEEKABILIDAD, no "siempre m3u8/mpd":**
1. 🥇 **Directo H264/AAC/MP4 con HTTP Range** → play directo = **seek instantáneo** (lo "vuela").
2. 🥈 **Pipeline RD-mediaInfos** (modelUrl) como fallback universal:
   - formato: **HLS para iOS/Safari**, **DASH/Shaka para Android/desktop/TV**.
   - audio: `spa*` → `eng*` (de `details.audio`).
   - calidad: elegir por dispositivo/red (cap 1080p en TV; bajar a 720p en red débil).
     ⚠️ NO es ABR real: cada calidad es un stream de bitrate único (1 Representation).
   - subtítulos: slot `{subtitles}` del modelUrl si `details.subtitles` los trae; si no, OpenSubtitles (ADR-005).
3. Esto **resuelve de raíz** HEVC-en-TV, MKV-seek, AC3/DTS, multi-dispositivo (RD transcodifica/empaqueta).

## Límite conocido (honesto)
El seek lejano (+30min) sobre transcode RD **siempre lagea**: RD genera segmentos `.m4s` on-demand
(confirmado: cuelga igual en HLS y DASH). NO se arregla sin pre-encode/CDN propio. Mitigaciones:
maximizar el camino directo-Range (1), recuperación+backoff (ya implementado), y **pre-warming**
(resolver/cachear al abrir la ficha).

## Plan por fases (2026-06-14)
- **Fase 1:** `mediaInfos` como camino canónico + atajo directo-Range. Selección directo-vs-mediaInfos
  por seekabilidad (absorbe el scoring MP4+H264). Validar desktop/TV/celular.
- **Fase 2:** formato por dispositivo (HLS iOS / DASH resto) + calidad por dispositivo/red.
- **Fase 3:** subtítulos desde RD (cuando existan embebidos) vs OpenSubtitles.
- **Fase 4 (opcional):** pre-warming en la ficha.
