# Sesión 2026-06-10 — MaldoxFilm

## Contexto
Sesión enfocada en arquitectura del reproductor RD (flujo server-side), decisión de
subtítulos, y optimización de memoria para TV/móvil.

## Trabajo realizado

### Arquitectura RD server-side (ADR-004) — implementada
- **Hallazgo (con el usuario):** el camino no-cacheado reproducía la URL
  `torrentio.../resolve/{TOKEN}/...` → Torrentio de puente (rompe Range, expone token),
  y no disparaba cacheo (caso "Weapons"). El token también viajaba en la URL pública.
- **Nueva Netlify Function `netlify/functions/rd-stream.js`** (server-side, ESM):
  `addMagnet → torrents/info → selectFiles → info(status=downloaded?) → unrestrict/link →
  streaming/transcode`. Itera VARIOS infoHashes (coma-separados), salta los bloqueados
  por DMCA (error 35), prioriza **DASH**, devuelve `liveMP4`/HLS de respaldo. Maneja
  errores 33/21/34/5/429. El token NUNCA sale del servidor.
- **Cableado (diseño inyectable, tests intactos):**
  - `types/index.ts`: campos `serverDashUrl`/`serverLiveMp4Url`/`serverHlsUrl`/`serverDirectUrl`.
  - `rdStream.ts`: opción `serverResolve` (default no-op); si NO hay `rdId`, pasa los
    infoHashes del pool a la function y puebla esos campos.
  - `bootstrap.ts`: `serverResolve` real → `fetch('/.netlify/functions/rd-stream?...')`.
  - `usePlayer.ts`: si viene `serverDashUrl` → reproduce con Shaka directo (multi-audio + Range).
- **Prioridad de capas (verificado):** 1) cacheado (rdId) · 2) rescate del pool
  (versión ya cacheada, sin escribir en RD) · 3) server-side rd-stream (último recurso,
  escribe). Weapons se resuelve hoy en la capa 2 (x264-DDP cacheada en pos 14 del pool).
- **Estado:** cableado + cached path verificado intacto (251 tests). **Falta probar el
  `ready:true` real** (necesita título con CERO versiones cacheadas; solo vimos error 35
  en la versión DMCA al probar el endpoint aislado).
- **Endurecimiento del camino de éxito (revisión de código, nunca había corrido):**
  se halló el bug que impedía `ready:true`: RD es asíncrono y la función chequeaba el
  estado UNA vez sin esperar → tras `addMagnet` el torrent está en `magnet_conversion`
  (sin `files`) → reportaba `no_video`; y aunque estuviera instant-cacheado tardaba
  1-2s en marcar `downloaded` → reportaba `not_cached`. **Fix:** `pollInfo` con
  presupuesto GLOBAL (`TOTAL_BUDGET_MS=9000` para no exceder el timeout de Netlify):
  espera a que aparezcan `files` (`FILES_WAIT_MS`), luego a `status='downloaded'`
  (`CACHE_WAIT_MS`); corta candidatos al agotar el `deadline`; detecta estados muertos
  (magnet_error/error/dead/virus); selecciona SOLO el video (links[0] correcto);
  devuelve `torrentId` (para ADR-006). Cadena cliente verificada coherente de punta a
  punta (bootstrap→rdStream→usePlayer). `node --check` OK.

### Optimización de memoria (TV/móvil) — #1 aplicada
- **Recuperado `content-visibility: auto` + `contain-intrinsic-size`** en `Carousel`,
  `ContinueWatching` y `TopNumbered` (estaba en el original, se había perdido al migrar).
  El navegador no renderiza secciones fuera de viewport → mucha menos RAM en el Inicio →
  evita que TV/móvil se "peguen". Visualmente imperceptible. Tests 251/251.

## Decisiones
- ADR-004 (RD server-side para no-cacheado), ADR-005 (subtítulos = OpenSubtitles).
- Rechazado: rediseño del reproductor con Tailwind (el proyecto usa CSS scoped; el player
  ya está hecho, responsive y fiel 1:1). La limpieza Shaka/video del cliente YA existía.

### Optimización de memoria #2 + recuperación de stall (TV/móvil)
- **Buffer de Shaka recortado**: helper `isLowMemoryDevice()` (`navigator.deviceMemory ≤ 4`
  o UA móvil/TV) → `bufferBehind: 10` (de 30s default). Desktop intacto. (`usePlayer.ts`)
- **Recuperación de stall a mitad de reproducción (DASH)**: el watchdog original solo
  cubría el arranque; ahora un monitor (`setInterval` 2s) vigila que `currentTime` avance.
  Si se traba ≥8s en play (típico: pausar varios minutos → URL de RD caduca → "se pega"),
  recarga el mismo DASH desde la posición (`_shakaLoad` con `startTime`). Tras 3 intentos
  seguidos sin éxito → `onFallbackToNextSource`. Respeta `isStale`, se limpia en `destroy()`
  y al iniciar otra fuente; no interfiere con pausa/seek/cambio de audio. Tests 251/251.

### Empaquetado por dispositivo (recomendación, NO implementado)
- Discutido: PWA primero (universal, sin builds); luego nativo para "ícono en la TV":
  LG webOS `.ipk`, Samsung Tizen `.wgt`, Android/AndroidTV Capacitor `.apk`, iOS `.ipa`.
  Aviso: distribución realista = sideload (tiendas no aprueban apps de streaming RD).
  El empaquetado NO mejora la fluidez por sí solo; lo que fluidiza es la perf del web app.

### ADR-006 — limpieza de torrents de RD (IMPLEMENTADA)
- Function `rd-cleanup.js` (`DELETE /torrents/delete/{id}`, server-side, tolera 404).
- `torrentId` propagado: `rd-stream` → `bootstrap.serverResolve` → `ServerResolveResult` →
  `SelectedStream.serverTorrentId` → `usePlayer`.
- `usePlayer` guarda `currentServerTorrentId` y llama `cleanupServerTorrent()` en `destroy()`
  y al inicio de `loadRdSource`. `VideoPlayer.vue` pasa `serverCleanup` con `navigator.sendBeacon`.
- `serverCleanup` inyectable (default no-op). `vue-tsc` OK, tests 251/251, build OK.

### Deploy — BLOQUEADO (config, no código)
- `maldoxfilm-vue` **no es repo git** (sin `.git` ni remoto) → no se puede "commit".
- La carpeta **no está vinculada a un sitio Netlify** (`netlify status` lo confirma).
- Pendiente con el usuario: decidir git (init/remoto o saltar) y `netlify link` al sitio
  existente; además **`RD_TOKEN` debe estar seteado en las env vars de Netlify** (secreto,
  lo setea el usuario) para que las functions RD anden en prod.
